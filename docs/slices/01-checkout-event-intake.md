# Slice 1 — Checkout Event Intake

**Project:** Checkout Intelligence  
**Status:** Proposed for review  
**Slice type:** Vertical slice  
**Primary capability:** Event intake and persistence  
**Depends on:** Problem discovery, requirements, architecture decisions, domain model and event contract.

## 1. Business purpose

Checkout Intelligence cannot analyze checkout behavior unless it can receive and preserve trustworthy records of what happened.

This slice establishes the first end-to-end capability: accepting a checkout event through a documented HTTP API, validating its contract, storing it, and returning a predictable response.

The initial scenario uses a simulated storefront for the hypothetical Lecadence Decor merchant.

This is a technical demonstration of event intake, not evidence that the proposed product has already solved a real merchant's checkout problem.

## 2. User story

As a developer integrating a merchant storefront with Checkout Intelligence, I want to submit a valid checkout event through a documented interface so that the system can preserve the event for later analysis.

As the operator of Checkout Intelligence, I want invalid events and repeated deliveries handled predictably so that unreliable inputs do not silently corrupt future metrics.

## 3. Scope

### Included

- A documented event-ingestion endpoint.
- An explicitly defined event request contract.
- Request validation.
- Server-assigned receipt timestamps.
- Trusted demo merchant context.
- PostgreSQL persistence.
- Duplicate-event handling.
- Predictable success and error responses.
- Automated unit and integration tests.
- A documented way to run the slice locally.

### Excluded

- Full checkout journey reconstruction.
- Funnel calculations and dashboards.
- Finding generation.
- AI calls.
- Real payment processing.
- A production authentication and merchant-onboarding system.
- Platform-specific ecommerce connectors.
- Queues and background workers.
- Intervention tracking.

These exclusions keep the slice focused. They do not imply that the eventual product will never need those capabilities.

## 4. Proposed event contract

The initial endpoint will accept a JSON request with the following fields:

| Field | Type | Rule |
|---|---|---|
| `event_id` | UUID | Required; generated by the event producer and stable across retries |
| `event_type` | String | Required; must be in the supported event-type allowlist |
| `event_version` | Integer | Required; initially `1` |
| `journey_id` | UUID | Required for this initial demo slice |
| `occurred_at` | Timestamp | Required; ISO 8601 with an explicit timezone |
| `source` | String | Required; initially allow only the configured demo storefront |
| `properties` | JSON object | Required; validated against the selected event type |

The server will derive `merchant_id` from the configured demo integration context rather than trusting a client-supplied merchant identifier.

The server will assign `received_at` when it receives the event. Clients must not control this value.

The contract is a proposed starting point. Its details must be reviewed before implementation.

### Initial event types

Use a small allowlist for the demo:

- `product_added_to_cart`
- `checkout_started`
- `delivery_details_submitted`
- `payment_attempted`

Each event type must have a defined meaning and an explicit policy for its `properties`.

For example, `payment_attempted` means that a payment attempt was reported. It does not mean that the payment succeeded.

Do not include arbitrary personal information or payment details in event properties. Use synthetic demonstration values.

`checkout_completed` is deliberately deferred until the distinction between a client-reported completion and an authoritative order outcome has been defined for the demo.

## 5. Identity and duplicate handling

The producer generates an `event_id` before sending an event and reuses the same ID when retrying delivery of that event.

The proposed idempotency rule is:

- First valid delivery: persist the event and report that it was accepted.
- Repeated delivery with the same event identity and equivalent event content: do not create another event; return a response that identifies it as a duplicate.
- Repeated identity with conflicting content: reject the request as an identity conflict.

The uniqueness boundary should be the trusted merchant identity plus `event_id`.

The persistence operation must enforce uniqueness at the database level. An application-level check alone is not sufficient because concurrent requests can race.

A duplicate must not be counted as a new checkout occurrence in later analytics.

For this initial slice, equality should be evaluated using the normalized, validated event content, excluding server-assigned receipt metadata. The implementation must document the normalization rules it uses.

## 6. Request-processing flow

The expected flow is:

1. Receive the HTTP request.
2. Resolve the configured demo merchant context.
3. Validate the request envelope and event-specific properties.
4. Normalize the validated values according to the contract.
5. Attempt to persist the event under the agreed uniqueness constraint.
6. Distinguish a new event from a duplicate or conflicting event identity.
7. Return a documented response.
8. Record appropriate operational logs without unnecessarily logging event properties.

The request should not trigger AI analysis or expensive downstream processing.

### Error behavior

The exact response schema will be specified in the API design, but the expected semantics are:

- Malformed JSON or invalid field values: client error.
- Unsupported event type or version: client error.
- Invalid event-specific properties: client error.
- Repeated event with conflicting content: conflict response.
- Database unavailable or persistence failure: server error without exposing internal details.
- Valid new event: successful acceptance response.
- Valid duplicate event: successful, explicitly identified duplicate response.

Use a consistent error representation. Do not expose database credentials, SQL details, stack traces, or internal exception messages to API clients.

## 7. Persistence requirements

Persist enough information to support future journey reconstruction and analytics.

At minimum, preserve:

- Event identity.
- Trusted merchant identity.
- Event type and version.
- Journey identity.
- Source-reported occurrence timestamp.
- Server-assigned receipt timestamp.
- Validated event properties.

The database must enforce the agreed event uniqueness constraint.

The implementation must use explicit transaction and error-handling behavior. An event must not be reported as newly accepted if it was not successfully persisted.

The exact SQLAlchemy model, table name, column types, indexes, and migration belong to the implementation design. They should reflect this contract rather than dictate the domain rules accidentally.

## 8. Architectural responsibilities

Keep responsibilities separate while implementing the vertical flow.

### API boundary

- Parse and validate HTTP input.
- Resolve the trusted demo context.
- Convert domain or application outcomes into HTTP responses.

### Application layer

- Coordinate the event-intake use case.
- Apply the agreed identity and duplicate-handling behavior.
- Request persistence through an explicit dependency.

### Domain layer

- Define event identity and validation rules that belong to the domain.
- Represent supported event types and their meaning.
- Avoid depending on FastAPI, SQLAlchemy, or HTTP response objects.

### Persistence infrastructure

- Store and retrieve events.
- Enforce database constraints.
- Translate relevant database outcomes into application-understandable results.

These are logical responsibilities, not a demand to create an empty folder or class for every possible concept. We should create only the files required to implement this slice cleanly.

## 9. Acceptance criteria

The slice is complete only when the following behaviors are demonstrated by automated tests:

1. A valid supported event can be submitted through the API.
2. A newly accepted event is persisted and can be verified in the database.
3. The server assigns a receipt timestamp.
4. The event's occurrence timestamp is preserved.
5. Invalid requests are rejected without creating event records.
6. Unsupported event types and versions are rejected.
7. Invalid event-specific properties are rejected.
8. Repeated delivery of the same event does not create another record.
9. A repeated identity with conflicting event content is rejected.
10. Concurrent duplicate submissions cannot create duplicate records.
11. Database failure does not produce a false success response.
12. Error responses do not reveal internal infrastructure details.
13. The API does not trust a client-supplied merchant identity.
14. Tests run locally without requiring a paid external service.
15. The documented local setup and test commands work from a clean project environment.

Tests should verify observable behavior rather than merely assert that internal methods were called.

## 10. Test strategy

### Unit tests

Test contract validation and domain rules independently of the database and HTTP server.

Examples:
- Valid event envelope.
- Unsupported event type.
- Invalid timestamp.
- Invalid event-specific properties.
- Event identity and duplicate-content comparison.

### API tests

Test the HTTP contract.

Examples:
- Successful submission.
- Invalid request response.
- Unsupported event response.
- Duplicate response.
- Identity-conflict response.
- No internal exception details in server-error responses.

### Database integration tests

Use PostgreSQL to verify persistence and database-enforced uniqueness.

Examples:
- Stored values match normalized input.
- Duplicate delivery creates one event record.
- Concurrent duplicate delivery remains safe.
- Transaction or database failures do not result in false acceptance.

Mocks may help with unit tests, but they do not replace PostgreSQL integration tests for database constraints and transaction behavior.

## 11. Definition of done

This slice is complete when:

- The API contract is documented.
- The endpoint works end to end.
- The database migration can create the required schema.
- The tests pass.
- Local setup and execution are reproducible.
- The event identity, duplicate, timestamp, and error semantics are documented.
- The changes are reviewed and committed.
- The slice's known limitations are recorded.

The slice does not need a finished dashboard, AI analysis, or a production deployment to be complete.

## 12. Known limitations

- The demo merchant context is configured locally; this is not production tenant authentication.
- Only the initial supported event types are accepted.
- Journey reconstruction and funnel calculations are not implemented yet.
- No authoritative order or payment outcome is recorded by this slice.
- No guarantee of delivery is provided beyond the API's documented persistence response and producer retry behavior.
- Hosted free-tier availability is not required for local development.

## 13. Next step

Review the proposed event semantics and acceptance criteria. Then specify the exact API request and response schemas, validation rules, and persistence constraints.

After those are agreed, implement this slice incrementally, writing tests alongside the corresponding behavior and committing at meaningful checkpoints.
