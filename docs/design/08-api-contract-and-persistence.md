# API Contract and Persistence Design

**Project:** Checkout Intelligence  
**Status:** Proposed for review  
**Scope:** Slice 1 — Checkout Event Intake  
**Endpoint:** `POST /v1/events`

## 1. Purpose

This document turns the Slice 1 requirements into an implementable HTTP contract and persistence design.

It defines what an integration client sends, how Checkout Intelligence validates and accepts events, how repeated requests are handled, and what the database must guarantee.

This is an initial demo contract, not a claim of compatibility with any real ecommerce platform.

## 2. API boundary

The integration client communicates with Checkout Intelligence through an HTTP API.

The client does not:
- Access the Checkout Intelligence database directly.
- Import internal Python modules.
- Choose its own trusted merchant identity.
- Set the server's receipt timestamp.
- Declare that a payment succeeded merely by reporting a payment attempt.

For the initial local demo, the server uses a configured demo merchant context and accepts events only from the configured demo source. This is a development arrangement, not production authentication.

## 3. Endpoint definition

### Request

`POST /v1/events`

Content type: `application/json`

The request contains the event envelope and event-specific properties.

### Successful responses

- `201 Created`: A new event was validated and persisted.
- `200 OK`: An equivalent event with the same identity had already been persisted.

### Error responses

| HTTP status | Meaning |
|---|---|
| `400 Bad Request` | Malformed JSON or invalid request syntax |
| `409 Conflict` | The event identity already exists with different normalized event content |
| `422 Unprocessable Entity` | A structurally valid JSON request violates the event contract |
| `503 Service Unavailable` | The persistence dependency is unavailable |
| `500 Internal Server Error` | An unexpected server failure occurred |

All error responses use the common error structure defined below. The API must not return internal exception details, SQL statements, credentials, or stack traces.

## 4. Request schema

The request body has this conceptual shape:

```json
{
  "event_id": "b8b0d4b1-4db2-4f0b-8c4f-6d0b74b79a42",
  "event_type": "checkout_started",
  "event_version": 1,
  "journey_id": "29a19f40-47f8-4e7a-8d24-4f2dfdfbe4e5",
  "occurred_at": "2026-10-29T10:15:00Z",
  "source": "demo-store",
  "properties": {}
}
```

The identifiers and timestamp above are illustrative values.

### Field rules

| Field | Rule |
|---|---|
| `event_id` | Required UUID generated by the producer and reused for retries of the same event |
| `event_type` | Required member of the supported event-type allowlist |
| `event_version` | Required integer; initially only version `1` is accepted |
| `journey_id` | Required UUID for this initial slice |
| `occurred_at` | Required ISO 8601 timestamp with an explicit timezone |
| `source` | Required; initially must equal `demo-store` |
| `properties` | Required JSON object matching the selected event type's schema |

Additional rules:

- Reject unknown envelope fields rather than silently ignoring misspelled or unsupported fields.
- Reject booleans where an integer is required.
- Normalize UUIDs to a canonical representation.
- Normalize timestamps to UTC for storage and comparison while preserving the same instant.
- Reject timestamps without a timezone.
- Apply reasonable request-body and field-size limits.
- Do not accept `merchant_id` or `received_at` from the request.
- Do not accept arbitrary personal information or payment credentials in `properties`.

The exact maximum request size and timestamp tolerance should be configured explicitly before implementation rather than left unlimited.

## 5. Initial event-specific schemas

The first version supports four event types. These property schemas are intentionally small so that every accepted field has a defined meaning.

### 5.1 `product_added_to_cart`

Required properties:

```json
{
  "product_ref": "DECOR-001",
  "quantity": 2
}
```

Rules:
- `product_ref` is a non-empty synthetic product reference.
- `quantity` is a positive integer.
- The property object contains no unsupported fields.

This records a reported cart interaction. It does not prove that a purchase occurred.

### 5.2 `checkout_started`

Required properties:

```json
{}
```

No additional properties are accepted in version 1.

This event means the configured source reported that checkout started.

### 5.3 `delivery_details_submitted`

Required properties:

```json
{
  "delivery_method": "standard"
}
```

For the initial demo, `delivery_method` must be one of:
- `standard`
- `express`
- `pickup`

This field identifies a simulated delivery choice, not a delivery address. Names, street addresses, phone numbers, and other personal details are unnecessary for this slice.

### 5.4 `payment_attempted`

Required properties:

```json
{
  "payment_method_category": "card"
}
```

For the initial demo, `payment_method_category` must be one of:
- `card`
- `bank_transfer`
- `other`

No card number, security code, bank credentials, or other payment credentials may be included.

This event means a payment attempt was reported. It does not establish payment success, failure, or order creation.

## 6. Response schemas

### 6.1 New event accepted

HTTP status: `201 Created`

```json
{
  "status": "accepted",
  "event_id": "b8b0d4b1-4db2-4f0b-8c4f-6d0b74b79a42",
  "received_at": "2026-10-29T10:15:01Z"
}
```

The response confirms that the event was persisted successfully.

`received_at` is assigned by the server and represents the receipt time of the original accepted event.

### 6.2 Equivalent duplicate

HTTP status: `200 OK`

```json
{
  "status": "duplicate",
  "event_id": "b8b0d4b1-4db2-4f0b-8c4f-6d0b74b79a42",
  "received_at": "2026-10-29T10:15:01Z"
}
```

The original event remains unchanged. A duplicate request does not create another record or replace the original receipt timestamp.

The client can safely interpret this response as confirmation that the event already exists.

### 6.3 Error response

All errors use a common structure:

```json
{
  "error": {
    "code": "event_identity_conflict",
    "message": "This event ID already exists with different event content."
  }
}
```

The `code` is stable and suitable for client-side handling. The `message` is safe for API consumers.

Field-level validation errors may include a structured list of invalid fields, provided it does not expose sensitive input or internal implementation details.

Proposed error codes include:
- `malformed_request`
- `invalid_event`
- `unsupported_event_type`
- `unsupported_event_version`
- `event_identity_conflict`
- `service_unavailable`
- `internal_error`

## 7. Event identity and idempotency

The uniqueness boundary is:

`(merchant_id, event_id)`

The server obtains `merchant_id` from its trusted integration context.

### Case A — New identity

If the identity does not exist:
1. Validate and normalize the request.
2. Persist the event.
3. Assign the receipt timestamp.
4. Return `201 Created`.

### Case B — Same identity and equivalent content

If the identity exists and the normalized event content is equivalent:
1. Preserve the original record.
2. Do not create a second event.
3. Return `200 OK` with the original `received_at`.

For equivalence, compare the normalized contract fields, including event type, version, journey ID, occurrence instant, source, and properties. Exclude server-generated receipt metadata.

### Case C — Same identity and conflicting content

If the identity exists but the normalized event content differs:
1. Preserve the original record.
2. Do not overwrite it.
3. Return `409 Conflict`.

### Concurrent requests

The application must not rely on a check-then-insert sequence alone.

Two requests may both check for an event before either has inserted it. PostgreSQL must enforce uniqueness, and the application must resolve the result of concurrent insertion attempts safely.

A suitable implementation is a transaction using the database uniqueness constraint and an insert-on-conflict strategy, followed by retrieval and comparison of the existing event where necessary.

Database errors other than the specifically handled uniqueness outcome must not be mistaken for duplicates.

## 8. Persistence model requirements

The initial event record must preserve:

- Event ID.
- Trusted merchant ID.
- Event type.
- Event version.
- Journey ID.
- Occurrence timestamp.
- Receipt timestamp.
- Source.
- Validated event properties.

### Database constraints

At minimum, enforce:

1. Primary identity for each stored record.
2. Uniqueness of `(merchant_id, event_id)`.
3. Required columns cannot be null.
4. Event version must be valid.
5. The application and database representation must preserve the intended timestamp semantics.
6. Properties must be stored in a representation suitable for JSON data and validated before persistence.

Application validation and database constraints serve different purposes. Application validation provides useful error responses; database constraints protect stored data against race conditions and invalid writes.

### Transaction behavior

The application must not return `accepted` before the persistence transaction succeeds.

If the transaction fails, the request must not produce a false success response.

If the connection fails after the database commits but before the client receives the response, the client may retry with the same event ID. Idempotency must make that retry safe.

### Indexing

The uniqueness constraint should support identity lookups. Additional indexes should be introduced only when query requirements justify them.

Journey and time-based indexes can be considered when we design journey reconstruction and analytics queries.

## 9. Validation and normalization order

Use this logical sequence:

1. Parse the request.
2. Validate the envelope fields.
3. Validate the event type and version.
4. Validate the selected event's properties.
5. Normalize identifiers and timestamps.
6. Resolve the trusted merchant context.
7. Compare or persist according to the idempotency rules.
8. Map the outcome to the documented HTTP response.

Implementation may resolve the configured merchant context earlier if required, but it must never trust an arbitrary client-provided merchant ID.

Validation errors must not create event records.

## 10. Testing requirements

### Contract tests

Verify:
- A valid request passes.
- Required fields cannot be omitted.
- Unknown fields are rejected.
- Malformed JSON is handled consistently.
- Invalid UUIDs and timestamps are rejected.
- Unsupported event types and versions are rejected.
- Event-specific property rules are enforced.
- Unsupported property fields are rejected.

### API tests

Verify:
- New events return `201`.
- Equivalent duplicates return `200`.
- Conflicting identities return `409`.
- Database unavailability returns the documented failure response.
- Internal exception details are not leaked.
- Clients cannot select arbitrary merchant ownership.

### PostgreSQL integration tests

Verify:
- Stored fields match normalized input.
- The uniqueness constraint is effective.
- Repeated delivery creates only one record.
- Concurrent submissions of the same event remain safe.
- A failed persistence operation does not report success.
- The original event and receipt timestamp remain unchanged after duplicate delivery.

Use PostgreSQL for tests of PostgreSQL-specific behavior. SQLite or mocks alone cannot prove that the intended uniqueness and concurrency behavior works against the actual database.

## 11. Open decisions before implementation

The following details still need explicit decisions:

- Maximum request-body size.
- Maximum permitted lengths for string fields.
- Timestamp tolerance and handling of implausibly future-dated events.
- Exact JSON normalization behavior for comparison.
- Exact database column types and migration structure.
- Whether to store normalized content or a canonical content hash for duplicate comparison.
- Exact trusted demo configuration mechanism.
- Whether the demo endpoint requires a local API key or another minimal access control.
- Exact readiness behavior when PostgreSQL is unavailable.

Do not invent production guarantees beyond the scope of this initial implementation.

## 12. Definition of done

This design is ready for implementation when:
- The request and response schemas are understood.
- Event-specific property rules are agreed.
- Duplicate and conflict behavior is explicit.
- The persistence uniqueness guarantee is defined.
- The test cases cover normal, invalid, duplicate, concurrent, and failed-persistence paths.
- The remaining configuration decisions are recorded.
